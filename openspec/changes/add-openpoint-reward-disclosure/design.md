## Context

水電 walking skeleton 的終點目前是 `provider_confirmed`（`waitingFor` 為 null），沒有「服務完成」與「驗收」。使用者要求的是**在訂單成立時就先告知預計回饋**，因此本變更刻意不引入新的 stage，只在既有的 accept 分支加上揭露，讓 blast radius 維持最小。

## Decisions

### 為什麼把「預計」和「實際發放」分開

主辦資料集的 `point_status` 有四個狀態，並用 `complete_time` 判斷發放時機，訂位類訂單甚至區分 `70 已完成（預定時間後 3 小時）` 與 `80 已完成（7 天後核銷）`。這代表「應獲得點數」與「已發放點數」在來源系統本來就是兩件事。

本階段只做前者，狀態固定 `01 待發放`。如果現在就把揭露寫成「已獲得」，之後補上完成流程時會需要回頭改契約與 UI 文案，也會在 Demo 時給出錯誤承諾。

### 為什麼金額來源要出現在契約裡

點數必須有計算基礎，但這個 skeleton 沒有報價引擎。三個選項：廠商回報、價目表估算、固定點數。選擇廠商回報並保留類別基準作為 fallback，因為：

- 廠商是唯一知道實際金額的角色，這也對應 `mms_order_record.final_amount` 由服務商提供的設計。
- 完全不看金額（固定點數）會讓 `final_amount` 與 `earn_points` 兩個欄位失去意義。
- 純價目表估算需要先做報價引擎，超出本變更範圍。

fallback 必須在契約裡帶 `amountSource`，否則前端無法區分「廠商說 2800」與「平台猜 2800」，住戶會把估算值當成報價。

### 為什麼用萬分位整數而非浮點費率

`0.01` 在二進位無法精確表示，`amount * 0.01` 在不同平台可能產生 `27.999999999999996` 這類結果，取整後就會出現一分錢差異。點數是對住戶的承諾，同一筆訂單在 Flask Lambda 與 AgentCore Runtime 算出不同點數是不可接受的。費率以萬分位整數表示後，`basis_amount * rate_bp // 10_000` 全程整數運算，結果完全確定。

### 為什麼金額驗證要在交易外

現有的 accept 已經有相同模式：`arrivalWindow` 缺失時在進入 `store.idempotent` 前就擋掉，避免不合法的 accept 消耗掉 pending task 或推進版本號。金額驗證沿用同一位置，否則廠商填錯金額會導致任務被吃掉、必須等平台改派。

### 為什麼不現在建 ledger

append-only 的 `mms_point_ledger` 是實際發放的正確設計，但在只有「待發放」一種狀態時，ledger 只會有一種寫入方向，無法驗證它真正要解決的問題（發放、收回、退點的對帳）。等完成流程進來時一併設計，才有完整的狀態轉移可測。

## Risks

- **住戶把預計當保證**：金額來自廠商預估，實際完工金額可能不同。緩解方式是揭露文字明確標示「預計」、金額來源與發放條件；實際發放時要以完工金額重算而非沿用此值。
- **費率與上限寫在程式常數**：目前 `EARN_RATE_BASIS_POINTS` 與 `MAX_POINTS_PER_ORDER` 是模組常數。活動檔期或分級費率進來時需要外部化，但現階段外部化會增加沒有需求支撐的設定層。

## Open Questions

- 服務完成的觸發者：廠商回報完工即完成，或需住戶驗收？此決定會影響 `02 已發放` 的時機與是否需要 Step Functions 的 wait state。
- 冷卻期是否要真的用 Step Functions 實作，或先以 Flask 同步轉移代替。
